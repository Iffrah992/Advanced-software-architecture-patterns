# Claim stock atomically

**Date:** 2026-10-24
**Step:** 1 · **Pattern:** Layered (business + persistence) · **Problem:** P2 Overselling · **Requirements:** FR-6, FR-7, FR-13, DB-1

## Status

Accepted. Amended by [Keep hot stock in an in-memory grid](keep-hot-stock-in-memory-grid.md) — the same atomic rule moves from SQL to Redis.

## Context

With one pair left, Buyer A and Buyer B both read `available = 1`, both pass the check, both decrement. Stock becomes −1 and two orders are confirmed for one shoe. The root cause is that **check** and **take** are two separate steps, so two requests can interleave between them.

Options considered:

| Option | Pros | Cons |
|---|---|---|
| `SELECT … FOR UPDATE` then `UPDATE` (pessimistic lock) | Correct | Holds a row lock across two statements; makes P1 worse |
| Optimistic locking with `version` column and retry | No long lock | Under 10,000 concurrent requests almost all fail and retry → feeds P4 |
| **Single conditional update** `UPDATE … SET available = available - 1 WHERE available > 0` | One statement, atomic in the DB, no read-then-write gap, no retries | Still one hot row (addressed in Step 7) |
| Application-level `synchronized` | Simple | Only works in one JVM; breaks with several servers |

## Decision

Stock is claimed with one conditional update; the number of affected rows decides the result:

```sql
UPDATE inventory
SET    available = available - 1
WHERE  sale_id = :saleId AND available > 0;
-- rows = 1 → reserved      rows = 0 → sold out
```

The reservation row is inserted in the same short transaction. As a last line of defence, `inventory.available` has `CHECK (available >= 0)`. Releasing a unit (payment failed, TTL expired) uses the reverse update guarded by the reservation status, so a unit is returned exactly once:

```sql
UPDATE reservation SET status = 'RELEASED' WHERE id = :id AND status = 'ACTIVE';
-- only if 1 row changed:
UPDATE inventory SET available = available + 1 WHERE sale_id = :saleId;
```

## Consequences

- Overselling becomes impossible regardless of how many servers run (verified by T-2: 0 oversold in 100 runs).
- No retries are generated by lost optimistic races.
- All requests still serialise on one row, so P1 remains; this is addressed by the gate (Step 3) and the in-memory grid (Step 7).
